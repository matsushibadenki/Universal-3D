# エッジ／面索引の構築費用（2026-11-05）

🟢 [Done] `get_snap_diagnostics.surface_build` に、不変形状索引の構築履歴を追加した。頂点Map、境界抽出／重複排除、辺ソート、辺Bounds、辺BVH、面Bounds、面BVH、合計を経過µsで保持する。キャッシュ中の形状だけを集計し、物体・頂点の全走査を追加しない。

この値は現在キャッシュに残る索引の**初回構築履歴**であり、再利用時に当該ジョブが消費した時間ではない。失敗・取消の部分結果は公開しない。現在の読込費用は `get_load_profile` と併用する。各工程は逐次区間で、合計には計測・初期化等の小さな隙間も入る。

## 実装

- 元ポリゴンの辺マスクがある場合、境界判定に不要な法線／同一平面計算を省略する。マスクなしの旧形式では従来の境界・折れ目判定を維持する。
- 頂点Map・辺集合の容量を事前確保し、辺の正規順ソートとBounds計算を直接比較・成分演算にする。
- BVHの中央値比較用の中心座標を一度だけ計算する。葉サイズ8と分割規則からノード数を求めて事前確保し、Bounds走査も成分演算にする。
- 中心座標生成・Bounds走査・中央値分割後にも取消を確認する。問い合わせ、同点処理、Undo／Redoの所有規則は変更しない。

中心座標の一時バッファは木の完成後に解放する。`bvh_center_scratch_peak_bytes` は各木の中心座標Vec容量の最大値で、同時確保する他バッファやRSSの総量ではない。形状間の集計も最大値であり加算しない。既存の構築中合算予算と採用判定を通す。

## 実シーン比較

公開NVIDIA SimReady IV_pole_a01、revision `524747d9b5e1f21b5b18b56041788c01d745f1a1`（CC-BY-4.0）から作った同一の55,275,744-byte `.u3d`を使用した。16メッシュと既定Cube、合計458,726三角形。入力ハッシュ・環境・全試行は[生データ](benchmarks/surface-build-real-20261105.json)に記録した。

macOS / debugのヘッドレス読込を旧→新、新→旧、旧→新の順で各3回、別プロセスで実行した。計測中にビルド・テストは並行実行していない。OSキャッシュは消去していない。旧実装は本プロジェクト自身の変更前アルゴリズムを同じ計測点でテスト専用に保持し、ThreeXのコードは使用していない。

| 境界抽出 | 3519.27 | 2311.71 |
| 辺ソート | 980.64 | 451.45 |

索引構築中央値は約57.7%短縮した。ただし旧7.19〜14.21秒、新2.97〜17.11秒と大きく変動し、新の初回は旧より遅かった。工程ごとの中央値の和は合計の中央値と一致しない。読込全体の中央値は約9.3%短縮したが、解析時間にも変動があるため一般的な速度保証には使えない。

観測RSSピークの最大値は旧134,922,240 bytes、新134,987,776 bytes（ともに約128.7MiB）。瞬間ピークを保証しない。新の中心座標一時バッファ最大は1,036,872 bytes、保持索引バッファは旧41,038,184から新41,036,008 bytesへ変化した。容量管理値とプロセスRSSは別の指標である。

全6試行で最初の辺／面問い合わせはヒットし、取得時の全物体走査・形状生成は0件だった。自動テストでは旧／新の木の並び・Bounds・分割、葉境界の容量、マスク有無・縮退面の辺集合、既存の総当たり検索との一致を確認した。
