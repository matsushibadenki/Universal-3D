# CPUスナップ索引の保持目標と追い出し

2026-11-04。🟢 [Done] 既存キャッシュの管理対象バッファに保持目標を設け、参照のなくなった形状索引を追い出す。既定は128 MiB。使用中のシーン・選択元・旧ジェスチャーの参照を保護し、元のメッシュとUndo／Redoは保持する。

## 方針

対象はVertexCacheが保持する頂点・エッジ・各BVH・キャッシュ専用プリミティブ面のVec／Box容量と、現在の配置木のVec容量。既存のIndexMemory.buffer_bytesと同じ範囲である。形状の共有は一回だけ数える。HashMapバケット・構造体／Arcヘッダー・入力メッシュ・Undo／Redo・GPU資源はこの容量に含めない。現在のキャッシュから離れた旧スナップショットはこの保持目標の集計には含めない。構築の合算判定では別途計上する（後述）。

形状Geometryの強参照がキャッシュだけになった場合に、追い出し候補とする。取得・追加・配置解除の順序を記録し、候補の古いものから目標まで除去する。順序記録はキー単位の操作で、対象物体全体を走査しない。

現在の配置シーンや以前のジェスチャーが持つGeometry Arcは追い出さない。保護分が目標を超えても吸着先を欠落させず、超過量を報告する。配置木は強参照が共有されている間は保護し、共有されていない木の余剰容量は後述の規則で縮小する。これはRAMやRSSのハード上限ではない。

## 自動処理とAPI

文書／索引採用時と、描画revisionが変わった配置同期後に保持容量を確認する。同revisionで超過が続く場合と移動元の新規取得では、再確認を最大約500msに一回へ抑える。毎カーソル更新で全頂点や全物体を調べる処理は追加していない。確認はキャッシュ内の形状数に比例し、Vecの長さ・容量・参照数を読むだけで頂点や面の配列を走査しない。

設定と明示的な解放はRust／Tauri APIで行う。

| コマンド | 引数 | 動作 |
|---|---|---|
| set_snap_cache_budget | mib: 1〜4096の整数 | 保持目標を変更して不要分を整理 |
| trim_snap_cache | purgeIdle?: boolean | 通常は目標まで整理、trueなら参照のない形状をすべて整理 |
| get_snap_diagnostics | なし | 現在値と最後の整理結果を取得。索引の新規構築は行わない |

クライアントコードの例：

```ts
await invoke("set_snap_cache_budget", { mib: 64 });
const report = await invoke("trim_snap_cache", { purgeIdle: true });
```

設定はRustのEditorキャッシュに属し、各ウインドウで共有する。文書を開き直しても同じセッションでは保持する。文書形式やUndo項目へは保存せず、アプリ再起動時は128 MiBへ戻る。設定UI・永続化は今回追加していない。新規構築用のU3D_SNAP_INDEX_BUDGET_MIBは別の予算で、今回の保持目標を変更しない。

明示解放は、まだ同期されていない配置シーンを新しく構築しない。古い配置シーンが参照する形状は、次の通常同期まで保護される場合がある。旧ジェスチャーの保持が終わった直後も、反映は次回の整理まで遅れる。未参照分が目標内なら保持して再利用する。

## 診断

get_snap_diagnostics.retentionにはlimit_bytes、current_buffer_bytes、referenced_buffer_bytes、idle_buffer_bytes、over_budget_bytes、累積追い出し数／容量、last_trimを返す。referenced_buffer_bytesはGeometryの外部強参照分と現在の配置木配列を含む。物理メモリの最小必要量ではない。

last_trimは整理前後の管理バッファ容量と追い出した形状数／容量。累積値と目標はセッション内で継続し、文書世代を切り替えた際の古い整理結果は解除する。last_preparationはワーカーで準備した当時の容量のため、採用後に不要分を追い出せば現在の保持容量より大きくなる。

キャッシュから除去した容量は、OSへ即時返却された容量を表さない。元のMesh Arcは文書や履歴に残り、別の所有者・アロケータのページ保持もある。追い出しで管理対象バッファは減っても、RSSが減る保証はない。

## 検証と代償

通常Rust112件。新規3件で、古い未参照形状の選択・目標ぴったりの境界・繰返し整理、旧ジェスチャーの頂点／エッジ／面候補保護、最後の参照解放後にWeakが失効すること、Undoで元メッシュから索引を再生成すること、Redo後の再追い出し、文書・dirty・Redo保持、不正設定の拒否、設定の文書置換後継続、隠れた事前構築形状の整理、同revisionの物体走査増加なしを検証した。

大容量の合成計測は1プロセス・debug版の機能確認。231,361頂点・460,800三角形・461,760エッジ、元ポリゴン境界付き、Cubeを含む。保持目標を1 MiBに設定し、使用中／旧ジェスチャーによる保護と、解放後の整理を測定した。

| 状態 | 管理対象バッファ |
|---|---:|
| 表示中 | 37,346,788 bytes |
| 非表示後・旧ジェスチャー保持中 | 37,346,820 bytes |
| 旧参照を解放して整理後 | 2,040 bytes |
| 追い出した形状索引 | 37,344,780 bytes、1形状 |

この1回では整理16µs、Undo後の最初のエッジ探索は15.38秒だった。追い出し後は必要な索引を再生成するため、厳しい目標や明示解放により初回スナップが重くなる代償がある。Undoで文書データを戻す処理と、その後の吸着索引再構築は別の処理。時間は機器負荷・形状・ビルド設定に依存し、統計的な性能保証ではない。

RSSは表示時114,224 KiB、整理後114,368 KiBで、即時減少は観測されなかった。これは入力メッシュやアロケータ保持なども含むため、管理バッファ容量と別に扱う。元のMesh Arcを保存したままUndo後のエッジ探索を再開できることも確認した。[生データ](benchmarks/cache-retention-20261104.json)。

既存の工程別進捗表示とID付き取消を利用する（kind: snap）。取消／失敗ではDocumentや履歴を変更しない。操作適用前に文書stamp、描画revision、ツール、設定、選択、ドラッグtokenを照合し、不一致では操作を拒否する。完成した索引は操作がターゲットを取得するまでArcで保持し、保持目標を超えていても採用直後の追い出しを防ぐ。画面下端の取消ボタンとビューポートのEscapeで準備を取り消せる。

## 2026-11-04: 配置索引の容量回収と合算判定

`trim_snap_cache`は形状の追い出しに加えて配置木と配置／葉Mapを縮小する。配置木は空きノードを大きい添字から処理し、末尾の生存ノードを移して親・子・root・葉Mapの添字を修復する。別の木や全ノード用の変換配列は作らない。空き配列を解放し、VecとMapをshrinkする。検索結果・木の高さ／親子関係と、その後の追加削除をテストした。

通常同期では、必要ノード容量の2倍＋64 KiBを超える場合、またはMapのペイロード容量が生存配置の4倍＋64 KiBを超える場合に縮小する。形状が保持目標を超えるだけでは密な配置木を毎回縮小しない。明示的な未参照分解放はこの閾値によらず縮小を試みる。現在のSceneIndexに別の強参照がある場合はコピーしてまで縮小せず、`scene_compaction_deferred`として延期する。最後の参照が消えた後のアクセスで、既存の500ms間隔の再試行規則に従う。文書・選択・Undo／Redo・revisionは変更しない。

`last_trim`には`scene_reclaimed_buffer_bytes`と`scene_reclaimed_payload_bytes`を追加した。後者は配置／葉Mapのcapacity×エントリサイズの概算であり、HashMap制御バイトやアロケータのヘッダまでを示すものではない。

合算予算は現在キャッシュとは別に弱参照で生存する形状索引とSceneIndexを追跡する。Arcの同じ索引は一度だけ計上し、古い文書／ジェスチャーが保持する索引も含める。形状ハンドルと配置木・Mapの容量メタデータのみを確認し、全配置・頂点・面を走査しない。文書を置き換えても計上元と構築予約は引き継ぐ。詳細は[構築予算](snap-index-budget.md)。

### 合成計測

[単独実行の記録](benchmarks/scene-capacity-20261104.json)。50,001配置から32配置へ削減し、配置木で9,843,120 bytes、Mapペイロード容量で約4.5 MiBを回収した。旧スナップショットが生きている間は総計20,286,864 bytesを保護し、旧参照の解放後は17,976 bytesになった（初期20,270,120 bytes）。この実行の縮小処理は2,651µs。debugの合成シーン1回分であり、時間の保証・実RSS・割当のピークを表す数値ではない。HashMapの削除後capacityはハッシュ配置により少し変わり得る。
