# CPUスナップ索引の構築予算

初版2026-11-02、更新2026-11-04。🟢 [Done] .u3d読込・復旧・USD取り込みで、新しく準備するCPU索引の容量を構築前に見積もり、予算超過時は採用前に拒否する。入力メッシュの既存上限とは別の制御である。

## 設定と判定

既定512 MiB。`U3D_SNAP_INDEX_BUDGET_MIB`で1〜4096の整数を指定できる。Tauriアプリを起動するプロセスの環境へ設定する。無効な値は無視せず`SNAP_INDEX_INVALID_BUDGET`として失敗する。起動中に設定を変更するUIは今回追加していない。

```sh
# 開発起動の例
U3D_SNAP_INDEX_BUDGET_MIB=128 npm run tauri dev
# 合成シーンで設定値の反映を確認
U3D_SNAP_INDEX_BUDGET_MIB=16 python3 scripts/benchmark-snap-memory.py --prewarm-scene --cases shared --runs 1 --output /tmp/snap-budget.json
```

索引の構築用予約値は、次の保守的な重みで計算する。MiB=1,048,576bytes。

| 対象 | 予約値 |
|---|---:|
| 不変形状の三角形 | 1,024 bytes／三角形 |
| 表示配置（ミラーは追加1配置） | 1,024 bytes／配置 |
| 一意の形状 | 4,096 bytes／形状 |

形状の重みには、重複しない頂点・エッジ、Vecの余剰容量、頂点／エッジ／面BVH、トポロジーHashMapと一時領域の費用を見込む。配置の重みには、行列・境界・配置木・葉／配置Map・構築用の葉配列を見込む。プラットフォーム固有のアロケータをモデル化した厳密な上限ではなく、構築を許可するか決める概算値である。

同一Mesh Arcは別IDのエイリアスでも一回だけ数える。座標が等しくても別Arcなら別形状とする。非表示の参照メッシュは事前構築対象なので数え、未参照アセットは除外する。文書読込・復旧では表示中のプリミティブと表示配置も数える。隠れたプリミティブは今回事前構築しない。

計算はchecked演算で行い、桁あふれも拒否する。見積りが予算と同じなら許可し、1byteでも超えれば拒否する。USD用の形状束は全アセット参照を収集して判定してから、最初の形状を構築する。文書用は文書検証後、最初の索引構築前に全体を判定する。

構築中は各メッシュ完成後に索引所有Vec／Boxの保持容量の累計も予算と比較し、文書用は配置木完成後にも確認する。これは完成後の検査で、個々の割当を途中で制限するものではない。超過時は束を破棄して`SNAP_INDEX_BUDGET_EXCEEDED`を返す。予算超過の表示には英語・日本語・简体中文と容量を含める。

## 状態と診断

拒否時は文書・Undo／Redo・dirty・既存キャッシュを変更しない。復旧元を消費せず、チェックポイント書込にも進まない。USD変換やファイル解析の結果は索引の採用前に破棄する。ただしUSDのダウンロードキャッシュまで巻き戻すものではない。キャンセルは既存のチェックを継続する。

`get_snap_diagnostics`の`last_preparation.budget`に、成功した準備の`limit_bytes`、`estimated_working_bytes`、`triangles`、`instances`、`shapes`を記録する。`memory`／`buffer_bytes`は実際の保持バッファ容量で、予算の予約値と区別する。拒否結果で前回成功の記録は上書きしない。別epochの古い診断を表示しない規則も維持する。形状配列やパスをIPCへ追加していない。

## 合算判定（2026-11-04）

🟢 [Done] .u3d読込・復旧・USD追記・スナップのキャッシュミス再構築で、既存の生存索引と構築中の予約を合算して判定する。設定値の既定512 MiBは共通で、未参照キャッシュ保持目標128 MiBとは別である。

保持中容量は、形状索引のVec／Box、すべての生存SceneIndexの木Vec、および配置／葉Mapのcapacity×エントリサイズの概算を足す。弱参照で追跡し、同じArcは一度だけ計上する。現在キャッシュから外れた旧文書・ジェスチャーが保持する索引も対象。不要になった参照は次の集計で除外する。旧参照の解放直後は再集計まで多めに計上することがある。文書の置換でも集計元は引き継ぎ、全配置や全頂点は走査しない。

構築前に「既存容量＋他の構築予約＋今回の保守的見積り」をchecked演算で判定し、構築予約の追加はatomicに行う。文書全体の準備から呼ぶ形状準備は同じ予約を共有し、二重予約しない。予約はArcで完成結果と共に保持し、ワーカーのreturnから採用までの間も解放しない。各形状完成後・配置準備の128物体ごと・配置木完成後に、その時点の既存容量と予約を再判定する。保持容量が見積りを超えた場合は予約を増額できるか確認する。確定直前にもEditorロック下で再集計し、今回の保持容量と他の構築予約を含めて拒否できる。取消・失敗・unwind・結果破棄時は最後の予約ArcのDropで解放する。

`get_snap_diagnostics.admission`は`resident_index_bytes`、`reserved_working_bytes`、`combined_bytes`、`tracked_scenes`を返す。`last_preparation.budget`には予約時の`resident_bytes`、`concurrent_working_bytes`、`estimated_combined_bytes`も保存する。現在キャッシュのみの`buffer_bytes`、過去の準備時の記録、生存旧索引を含む合算値は範囲が異なる。数値のみIPCへ送り、索引データはRust内に置く。

## 範囲と限界

アプリ全体のRAM／RSS上限やVRAM上限ではない。入力文書・Mesh、Undoの元データ、USD SDK／変換・ダウンロード、GPU資源は対象外。HashMapはエントリ容量の概算を含めるが、制御バイト・ヘッダ・アロケータの内部状態は含めない。構築scratchは重み付き見積りであり、個々の割当を制限するアロケータではない。

通常編集時の索引同期／配置木COWは従来の経路で行う。新しい容量は集計へ反映し、進行中のワーカーと採用前の再判定が超過を検出するが、通常編集自体を予算で拒否する仕組みではない。保持中索引の保護と合算判定によって、空きRAMやOOM防止が保証されるものではない。保持目標の回収処理は[キャッシュ管理](snap-cache-retention.md)を参照。

ThreeXのstorage側で構築ジョブ制限と保持キャッシュ制限を分ける設計を参考にした。こちらの予約・弱参照集計・配置木の圧縮は独自に実装し、ソースの流用やリンクへの依存は追加していない。
